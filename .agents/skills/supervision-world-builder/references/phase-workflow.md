# 监督世界阶段工作流

本文件是 `$supervision-world-builder` 的操作参考。它描述阶段的输入、责任和完成证据；项目现役规则仍以仓库根目录 `AGENTS.md`、`README.md`、`docs/current-state.md`、`docs/architecture.md`、契约和 `frontend/DESIGN.md` 为准。

## 0. 前置核验与计划

主 Agent 先根据入口文本确定且只确定一个 `targetMode`：精确入口“开始制作监督世界，持续施工到完成”使用 `PUBLISH_OPEN`；调用者明确说“只审计”“只设计”或“只施工不发布”才使用 `BUILD_ONLY`。不向普通调用者提出模式选择题；若同一请求出现互相冲突的模式指令，先在计划记 `BLOCKED` 并请求澄清。

随后完成只读核验：仓库根目录、当前分支、工作树、现役发布清单、监督相关空位/既有资产、构建入口和敏感文件边界。第一步记录 Git 基线，包括 `git status --short --untracked-files=all`、当前分支、既有修改/未跟踪路径和计划候选写入路径。在确定每一阶段的写入集合后，都要将既有路径与写入集合比较；只要有任何重叠，立即把计划和阶段标记为 `BLOCKED`，请求决定并停止，子代理不得覆盖。若重叠的是计划文件本身，不得覆盖它；只读报告阻塞并请求决定。无重叠时原样保护他人改动，只在授权范围内继续；不 stash、清理或重写历史，必要时只在安全的干净状态执行 `git pull --ff-only`。

在计划文件没有重叠且可以安全写入时，先立即创建/更新 `docs/supervision-world-plan.md`，写入 `targetMode`、本批目标、明确排除项、Git 基线、候选 `writeSet` 和 `IN_PROGRESS` 的前置状态，再核验材料。原材料路径优先使用调用者显式给出的绝对或可解析路径；显式路径不存在、不可读或为空时也立即把前置阶段和计划记为 `BLOCKED`，请求修正并停止。没有给出时只检查仓库外的 `../project_materials/新人陪练案例库/监督`，禁止无界搜索；该默认路径不存在、不可读或为空时，立即把前置阶段和计划记为 `BLOCKED`，向调用者索要绝对路径并停止，不进入 A 阶段或任何其他写入。

材料通过后，再把材料绝对路径、发现的对象、预计批次和重叠检查结果补入计划；以后每一阶段确定新的写入集合时重复基线重叠门禁。

如果监督目录已有未完成内容，先在计划中标注 `KEEP / REWRITE / MERGE / MOVE / DEFER / DROP` 候选，不能由旧截图或旧计划直接推断为现役事实。

## A. 材料对象级只读审计

主 Agent 按对象边界拆分材料，直接派发多个只读子代理。一个子代理可负责一个材料族，但不能同时修改正式仓库。材料可能包含 DOCX、PDF、XLSX、PPTX、图片、表格、公式、嵌入对象或扫描页；子代理应使用宿主已提供的文档/表格/PDF能力或仓库脚本读取原始对象，而不是只看文件名或摘要。

每个报告至少回答：

- 对象、页/表/段落/图表位置和原始证据摘录或结构化转述；
- 可支持的业务对象、字段、状态、时间顺序、数字/公式、正常案例和跨来源关系；
- 可形成的认知动作与证据边界；
- 互相矛盾、缺字段、缺数字、缺正常流程或敏感信息；
- 可进入本批、应保持 `BUILDING/DEFER`、不能推断的内容。

主 Agent 只汇总报告和证据索引，不替代子代理做实质研究。材料缺口直接成为范围约束，不用泛化风险话术填充。

## A→B 拓扑冻结

主 Agent 根据审计报告冻结“最小、连续、可验证”的监督拓扑，并写清入口、前置、主链、分支、路线批次、暂缓主题和不改动的现役边界。拓扑设计本身交给设计子代理提出候选，主 Agent 负责取舍、范围冻结和计划登记。未有足够材料支撑的路线不进入正式发布，也不伪造地图进度。

## B0. 共享基础包

派发一个正式写入子代理，范围只包括共享基础包：字段字典、业务状态链、来源/证据索引、脱敏规则、正常案例骨架、通用结构化工作纸约定、共享 Decimal/日期/状态验证约定和必要的测试夹具。它不得开始任何 B1 路线或登记发布。

主 Agent 检查共享字段在原材料中的定位、脱敏后仍可核验、正常案例数字闭合、提交值与评分键未被改写，并更新计划后重新读取。

## B1…Bn. 路线批次

每批只处理计划中冻结的一组不重叠路线和对应文件。写入子代理必须完成：

1. route 内容的知识卡、正常示范、基础练习、综合实务；
2. 综合实务资料包与结构化工作纸，覆盖取数、计算/复算、账务或台账/报表填写、跨来源勾稽和结论；
3. Rubric 四维评分、硬性要求、定向补学目标及证据映射；
4. verifier/fixture/测试，使答案链、数值精度、状态迁移和安全投影可确定性验证；
5. 只在本批范围内更新相关来源索引或内容说明。

一批完成后子代理停止，不自行开始下一批。主 Agent 检查 diff、Schema、业务因果链、连续数字、答案和 Rubric，运行该批最小验证，记录证据和状态，再自动进入下一批（调用者已授权持续施工时）。

## C. 候选开放登记

所有路线内容、业务证据和本批确定性校验通过后，按计划的 `targetMode` 分流：

- `BUILD_ONLY` 不应用候选开放登记，保持监督世界 `BUILDING`，只保留内容/业务/确定性验证证据；完整监督世界浏览器验收在计划中记 `DEFERRED`，不得宣称正式开放闭环完成。
- `PUBLISH_OPEN` 单独派发登记子代理，把候选开放登记应用到当前未提交工作树。候选登记至少包含监督 map、新 release、sources、docs，以及使当前架构真正消费该 release 所需的最小 active selector/验证常量/相关测试接线。

登记子代理必须先阅读现役 `docs/architecture.md` 和代码，定位 `FormalContentCatalog` 的 active release selector、校验常量和相关测试；不得在 Skill 中预设文件名。只允许做让候选监督 release 可被当前架构加载/验证的最小发布接线，不得改通用契约、UI 结构、数据库、评分维度或视觉，不得偷偷改变其他世界。应用前重新执行基线与 `writeSet` 重叠门禁；应用后回报候选工作树的完整 `status`、diff、release/selector 关系和未提交状态。子代理不 commit、不 push、不清理、不回退他人改动。

主 Agent 复核候选 map、release、sources、docs、selector/验证接线、`BUILDING/DEFER` 边界和回退关系，并把候选工作树状态写入计划。候选登记不是正式 GitHub 发布；正式 commit/push 必须等 E 阶段浏览器验收通过。

## D. Fresh-context 去 AI 味

`PUBLISH_OPEN` 在候选开放登记已应用的工作树上启动全新上下文的 `gpt-5.6-luna`/`max` 子代理；`BUILD_ONLY` 可做路线/前端/后端的文字与代码审查，但不启动依赖开放态的完整浏览器验收。新上下文只读当前仓库、现役文档、候选内容和本 Skill 的验收要求，不读取施工者的自我辩护或旧审查结论。详细检查清单见 [fresh-context-humanization.md](fresh-context-humanization.md)。

建议顺序如下，写入路径重叠时串行：

1. 路线内容：知识卡、示范、练习、资料包、工作纸、补学文案；
2. 前端：动态状态、结果、反馈和历史展示，检查内部活动类型/字段 ID/状态码均通过业务中文映射；
3. 后端：评分证据、四维反馈、硬门槛、补学目标和重做提示；
4. `PUBLISH_OPEN` 候选工作树上的真实浏览器：完整浏览器闭环放在 E 阶段；本阶段只记录需要浏览器确认的文字、内部码或状态风险，再由指定写入子代理修复。`BUILD_ONLY` 不做正式开放态浏览器闭环，计划标记 `DEFERRED`。

每一轮必须说明保护的业务事实；主 Agent 以内容校验、契约测试和 diff 复核确认去味没有变成拓扑、视觉或评分改造。

## E. 候选工作树验收、提交与远端收口

主 Agent 根据 [acceptance-matrix.md](acceptance-matrix.md) 选择检查。

### `PUBLISH_OPEN`

1. 在 C 阶段已应用的未提交候选工作树上，重新运行内容/文字/契约确定性检查、后端测试、前端类型检查/构建、应用构建和必要的全量脚本；隔离 JAR/数据必须来自这份候选工作树，不能用未接入 active release 的旧构建替代。
2. 用真实桌面浏览器完成监督全链路：登录、知识卡、正常示范、基础练习、综合实务、第一次未掌握、定向补学、结构化重做、通过、下一节点解锁和历史查看。浏览器失败只修本批；每次修复后重新执行受影响的确定性检查和候选构建。相同具体阻塞连续两次仍失败，立即停止，不 commit、不 push、不清理或回退他人改动，并在计划回报候选工作树 `status`、diff 和失败证据。
3. 浏览器和全部验收通过后，主 Agent 最后复核敏感内容、`git diff --check`、`git status` 和候选登记范围，再 commit/push 当前跟踪分支。提交前不得把候选登记提前发布到远端。
4. push 后核对本地 `HEAD` 与远端当前跟踪分支的提交完全一致，并做最小开放态 smoke（必要时复用同一候选构建证据）：至少确认监督世界已开放、active release 可加载且首个正式节点可进入。若远端/本地不一致或 smoke 失败，停止并报告，不强推、不重写历史。

### `BUILD_ONLY`

只执行内容、业务和确定性验证；不应用候选开放登记，不切换 active release，不提交开放地图。完整监督世界浏览器验收标记 `DEFERRED`，不能宣称正式开放闭环完成。若调用者之后明确授权 `PUBLISH_OPEN`，必须重新经过 C 的候选登记和本节完整闭环。

## 计划状态格式

计划至少保持以下字段，完成一个阶段立即更新：

```text
targetMode: PUBLISH_OPEN | BUILD_ONLY
gitBaseline: status、分支、既有修改/未跟踪路径
writeSet: 当前阶段允许写入的精确路径
candidateWorktree: PUBLISH_OPEN 候选登记后的 status/diff/selector 与未提交状态；BUILD_ONLY=NOT_APPLIED
阶段 | 状态(PENDING/IN_PROGRESS/PASSED/BLOCKED/DEFERRED) | 子代理 | 文件范围 | 证据/验证 | 阻塞 | 下一动作
```

把 `BUILDING/DEFER` 主题、材料缺口、已保护的用户改动、重叠检查、候选工作树、最终提交/推送、远端一致性和开放态 smoke 信息分开记录。上下文压缩、重新进入或交接时先读计划，再读本文件中当前未完成阶段。
